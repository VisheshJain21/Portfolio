## Tech stack
- **Next.js (App Router) + TypeScript** — SSR, crawlable content
- **React Three Fiber + drei + GLSL** — 3D (quarantined in `webgl/`)
- **GSAP + ScrollTrigger + Lenis** — motion & smooth scroll (the site's animation backbone — every existing timeline/reveal/transition is GSAP)
- **Framer Motion** — added 2026-08-02 at user's explicit request for future component-level animation. ⚠️ Overlaps with GSAP (flagged to the user as redundant before adding — kept anyway per their call). Use GSAP for anything already covered by `animations/reveals.ts`/`gsap.ts`; reach for Framer Motion only for new, isolated component animation, not a parallel system for existing motion.
- **CSS + custom-property tokens** — no UI kit (no Tailwind, no shadcn)
- *Dependency rule:* a new dep must beat native CSS / Web Animations / existing GSAP before it's added.

## Architecture
**Hybrid, not all-WebGL.** All content in accessible/SSR DOM; WebGL layered in only at the hero + one or two accent moments. Separation of concerns: routing (`app/`) · presentation (`components/`) · data/copy (`content/`) · 3D (`webgl/`) · design tokens (`styles/`).

## Responsive invariants (durable — don't regress)
- **Root clip:** `html`/`body { overflow-x: clip }` — catches `position:fixed`/absolute descendants (nav overlay, marquees, warp layers) that `body`-only clipping can't. This is why phantom horizontal scroll kept recurring.
- **Global guards (`globals.css`):** `overflow-wrap: break-word` on text; `min-width: 0` on section grid/flex children (`[class*=grid|row|list|head] > *`) so they shrink instead of overflowing. Both via `:where()` (0 specificity, overridable).
- **Fluid tracks only:** grid columns use `clamp()`/`minmax(0,1fr)`/`minmax(min(Npx,100%),1fr)` — never a bare fixed px track in flow.
- **Gate:** `npm run check:responsive` (Playwright, headless) builds+serves+loads the site at 11 breakpoints 320→1920, FAILS on any horizontal overflow (names the offending element) or missing nav/hero/footer. Run it after ANY layout change. Script: `scripts/check-responsive.mjs`.
- **Perf gate:** `npm run check:perf` (Playwright) builds+serves, drives a real full-page scroll via dispatched wheel events (NOT `window.scrollTo` — this site's scroll is entirely Lenis-driven and `scrollTo` bypasses its RAF smoothing), once at native speed and once under 4x CPU throttling (simulates a mid-tier phone), collecting `longtask` entries. FAILS on any task over 200ms tagged **during the scroll itself** — a one-time task during initial page load (e.g. multiple WebGL canvases compiling shaders + GSAP building every section's ScrollTrigger in one synchronous burst) is reported but not failed on, since that's a different concern from "laggy while scrolling." Run after adding/changing any World layer. Script: `scripts/check-frame-perf.mjs`.

## APIs
- `GET /api/stats` — read-only, returns `{ views, likes }`. No side effects.
- `POST /api/view` — increments `view_count` unconditionally. Client guards to once/tab via `sessionStorage`.
- `POST /api/like` — body `{ liked: boolean }` = the new client-intended state (client already knows its own prior state from `localStorage`); server applies ±1, floored at 0. Two toggles net to zero — no separate rate-limiting needed.
- Storage: `src/lib/stats-db.ts`, single-row SQLite table via built-in `node:sqlite` (**must be a static top-level import** — both `require()` and `createRequire(import.meta.url)` fail under Turbopack with "Cannot find module 'node:sqlite': Unsupported external type Url for commonjs reference", and because the fallback logic is try/caught, either one silently demoted a live 330-view DB to an in-memory 0 with no visible error until the API response was checked by hand — this is exactly why the fallback path now `console.warn`s instead of failing silently). `engines.node: ">=22.5.0"` in `package.json` pins the floor `node:sqlite` needs. `globalThis`-cached to survive HMR. Open path is a fallback chain, not a single file: `./data/stats.sqlite` (persistent on `next dev`/`next start`/a VM) → OS temp dir (the only writable path on serverless — Vercel's project root is read-only; counts persist per warm instance, reset on recycle) → in-memory object (if neither location is writable, so the endpoints still answer 200 instead of 500ing). For durable counts on serverless, swap in Vercel KV/Turso/Upstash — `readStats`/`incrementView`/`setLike` is the only surface that would need to keep working.
